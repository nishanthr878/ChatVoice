# Proposal: Migrating the Node-Graph Orchestrator Toward Voice AI Vendor's Prerequisite-Gated Tool Calling

**Status:** Proposal, not a decision. This doc lays out the tradeoff and a concrete migration path; it does not commit to doing it. If a decision gets made, log it in `decisions-log.md` (new D-number) — this file stays the proposal, not the record of what was chosen. Grounded directly in this project's real source (`orchestrator/src/main/java/.../domain/orchestration/GraphExecutor.java`, `Flow.java`, `NodeHandler.java`, `domain/flow/CheckOrderStatusFlow.java`, `ProcessReturnFlow.java`, `IntentClassificationFlow.java`) against `target-main`'s real source (`agents/base/tools/shared.tsx`, `tools/return.tsx`, `goals/order-status/order-status.tsx`, `tools/index.ts`), not against `Voice AI Vendor-implementation-comparison.md`'s summary alone — every claim below was re-verified against the actual files.

## 1. What this project actually does today

`GraphExecutor.step()` runs a bounded hop loop (`MAX_HOPS_PER_TURN = 5`): each hop reads `conversation.current_node` from Postgres, dispatches to the `Flow` registered for the conversation's `flow_type`, and stops when `current_node` stops changing or a flow completes back to `intent_classification`. Each `Flow` (`CheckOrderStatusFlow`, `ProcessReturnFlow`, `IntentClassificationFlow`) owns a private `Map<String, NodeHandler>` — e.g. `ProcessReturnFlow`'s five nodes: `collect_order_id → lookup_order → check_threshold → auto_process | escalate_to_agent`. Every handler **imperatively** calls `conversationRepository.updateCurrentNode(conversationId, "next_node")` to advance — the transition graph is hardcoded Java control flow, not data. `IntentClassificationFlow.handleClassify` is a single upfront LLM call that picks one of four fixed buckets (`GREETING`/`CHECK_ORDER_STATUS`/`PROCESS_RETURN`/`OTHER`) and swaps `flow_type` — the *only* place an LLM influences which code path runs; every step after that is graph-hardcoded.

Two properties fall out of this, both already load-bearing elsewhere in the project's design:
- `ProcessReturnFlow.handleCheckThreshold` enforces the $10 approval threshold in pure Java (`foundLine.get().unitPrice() <= RETURN_APPROVAL_THRESHOLD`) — this is `decisions-log.md` D7 ("conditional/branching logic... is pure code, never an LLM call") made concrete.
- Digressing mid-flow doesn't work — `decisions-log.md` D19 explicitly names this as a known, deferred gap: `GraphExecutor` only re-classifies when `flow_type == "intent_classification"`, so nothing currently detects an off-topic message inside `process_return` and bails back to classification.

## 2. What Voice AI Vendor's actual code does (not the marketing description — the code)

There is no `current_node` anywhere in `target-main`. `tools/index.ts` is a flat array of registered tools (`GetOrderDetails`, `CheckReturnEligibility`, `ProcessMailInReturn`, ...). Each tool (`tools.registerTool({...})`) declares:
- `prerequisites: prereq.toolCall("CheckReturnEligibility", ["orderNumber", "orderLineId"])` — `ProcessMailInReturn` cannot run until `CheckReturnEligibility` was called *with matching* `orderNumber`/`orderLineId` params, checked by the platform before the tool function ever executes.
- A typed `params` schema (`toolParam.string(...)`, `toolParam.choice(...)`) instead of a hand-parsed extraction convention.
- A `func(ctx, params, controls)` returning `controls.result({ data, instructions })` or `controls.error(msg)` — never a bare user-facing string. `data` is machine-usable (`{ found: false, attemptsExhausted: true }`); `instructions` is guidance handed to the platform's own response composer, not spoken verbatim.

Which tool runs next is decided **fresh every turn** by the LLM/goal-agent, constrained by which tools' prerequisites are currently satisfied and by each tool's `description`. There is no equivalent of "the graph only has an edge from A to B" — the constraint is declarative and checked at call time, not structural.

**Critically, defensive re-checks still exist inside the tool bodies**, on top of the declared prerequisite. `ProcessMailInReturn.func` re-checks `getVerifiedOrderOwner(...)` and `mailInReturnEligible[...]` even though `CheckReturnEligibility` is a declared prerequisite. `CheckReturnEligibility.func` enforces the return-value threshold gate itself, in code (`thresholdExceeded`), exactly like this project's `handleCheckThreshold` — the LLM is never asked whether a return needs approval; the tool function decides and the LLM only sees the resulting `instructions`.

## 3. The load-bearing insight: this migration does not weaken D7

It would be easy to read "Voice AI Vendor lets the LLM pick the next step" as "Voice AI Vendor lets the LLM make the decisions D7 says must be pure code" — that would be a real regression, and worth rejecting outright if true. It isn't true. In Voice AI Vendor's code, **tool selection** (which function runs) is LLM-driven; **tool behavior once selected** (does this return get auto-approved) is still 100% pure code, exactly like today. `CheckReturnEligibility` never asks the LLM "is this over the threshold" — it computes it and returns a result the LLM can't override. The determinism guarantee simply moves from *"no graph edge exists to reach this outcome"* to *"the tool function refuses/redirects regardless of why it was called."* D7 survives this migration unchanged; it just gets enforced one level lower, inside the tool rather than inside the graph topology.

## 4. Concrete construct-by-construct mapping

| Today (node-graph) | Voice AI Vendor-style equivalent |
|---|---|
| `conversation.current_node` + `GraphExecutor.step()`'s hop loop | Dropped. Each turn: LLM proposes a tool call (or none); a dispatcher checks the tool's declared prerequisites against `tool_invocation`/`slot`, then executes. |
| `Flow` interface, one private `Map<String,NodeHandler>` per flow | A single flat tool registry (mirrors `tools/index.ts`), no per-flow ownership of a node map — already flagged as the natural evolution in `Voice AI Vendor-implementation-comparison.md` §8 (`Map<String,NodeHandler>` → `Map<String,NodeDefinition>`). |
| `NodeHandler.handle(...)` returning bare `String` | A `ToolHandler` returning a structured `Result(data, instructions)` / `Error(message)` — already flagged independently in `Voice AI Vendor-implementation-comparison.md` §2 and §10 item 5, so this piece is worth doing even if the rest of this migration is rejected. |
| `IntentClassificationFlow`'s fixed 4-bucket `switch` | Not strictly needed as a separate step — tool descriptions + prerequisites let the LLM pick `GetOrderStatus`-equivalent vs. a return-initiating tool directly. Open question below on whether a coarse pre-filter is still worth keeping for cost. |
| Scattered `slotRepository.saveSlot(...)` calls, one per field (`handleCollectDetails` makes 3 separate calls) | A single merge-patch write per turn, mirroring `store.ts`'s `capture(prev, patch)` — already flagged in `Voice AI Vendor-implementation-comparison.md` §3 as a portable fix independent of this migration. |
| `escalate_to_agent` node, hardcoded per flow (near-identical bodies in both `CheckOrderStatusFlow` and `ProcessReturnFlow`) | Becomes one shared `EscalateToAgent`-style tool, same shape as every other registered tool — not flow-owned, not duplicated. |
| Nothing today checks "was tool X already called with these args" — `tool_invocation.idempotency_key` only guards *re-execution*, not *ordering* | `tool_invocation` becomes dual-purpose: the existing idempotency check, plus the query a `prereq.toolCall(name, [paramNames])`-equivalent check needs ("find a completed invocation of X for this conversation whose args matched on these param names"). Very little new plumbing — the table this needs already exists for D8. |

## 5. What's genuinely harder, not just different — the real cost side

- **Loses the "impossible to reach the wrong state" guarantee for anything other than the D7-protected decisions.** `GraphExecutorReDispatchTest`'s whole testing approach (assert the exact `current_node` sequence a message produces) stops making sense — tests become "given this history, was the LLM's tool choice acceptable," which is a strictly weaker, more probabilistic thing to assert than "this code path is the only one reachable from here."
- **New failure mode: wrong-order or missed tool calls.** A hardcoded graph transition cannot be skipped by mistake. An LLM choosing among eligible tools can pick a technically-eligible-but-wrong one, or fail to call a required one at all. Voice AI Vendor's mitigation (prerequisites + rich descriptions + defensive in-function re-checks) makes these *recoverable*, not *impossible* — a real, accepted-by-Voice AI Vendor downgrade from this project's current guarantee, not a hidden one.
- **Real growth in prompt size, latency, and cost.** Today, `handleCollectDetails` sends one narrow, single-purpose extraction prompt per node — the project's own progressive-disclosure principle (`architecture-doc.md`: "only this node's relevant slots/instructions, not full history"). A flat tool-selecting LLM call needs the *whole* eligible-tool catalog (names, descriptions, prerequisites, params) plus enough conversation context to select correctly, every turn. This is the direct cost of trading determinism for flexibility, and should be measured, not assumed acceptable, before committing project-wide.
- **This is a genuine identity question for the project.** `context-doc.md` frames the whole point of this build as reverse-engineering *"a policy-bounded orchestration engine... structurally enforced."* `Voice AI Vendor-implementation-comparison.md` §1 already found that Voice AI Vendor's real code doesn't have a structurally-enforced *state graph* at all — only structurally-enforced *tool-call ordering* via prerequisites, with *tool selection* left genuinely open to the LLM. Adopting this fully is adopting the specific part of Voice AI Vendor's design that is less deterministic than what this project chose to build, not a strict upgrade — worth deciding on purpose, not by default momentum toward "be more like Voice AI Vendor."

## 6. What this migration would concretely fix

Worth stating plainly, since §5 is all cost: the D19-logged mid-flow digression gap (asking to start a return while inside `check_order_status` doesn't work, because nothing detects the off-topic message and re-routes) is close to structurally solved by this model — there is no rigid state to be "inside" that a digression needs to escape from. This is the one gap the current architecture has explicitly acknowledged and deferred that this migration would resolve as a side effect of the paradigm itself, not as a bolt-on fix.

## 7. Recommended path — staged, not a rewrite

Consistent with this project's own `decisions-log.md` D1 (two concrete flows before any generalized abstraction) and D6 ("upgrade only once the simple version's pain is actually felt"):

**Phase 1 — adopt the shape improvements regardless of the bigger decision.** These are correct independent of whether the graph itself ever changes, and de-risk Phase 2 by making the codebase structurally closer to Voice AI Vendor's idioms first:
1. `NodeHandler.handle(...)` → structured `Result(data, instructions)` instead of bare `String` (`Voice AI Vendor-implementation-comparison.md` §2, §10.5).
2. Batch slot writes into one merge-patch call per turn instead of scattered `saveSlot` calls (§3).
3. Extract the repeated `getSlot → isEmpty → escalate` guard into one shared helper (§4).

**Phase 2 — a reversible, single-flow pilot.** Rebuild exactly one flow as a flat tool registry with declared prerequisites and LLM-driven tool selection, leaving the other flow on the current `GraphExecutor`/`Flow` model untouched. Suggest `process_return`: it already has the richest branching (`collect → lookup → check_threshold → auto_process | escalate`) and is the flow D19's digression gap actually affects. This mirrors D1's original two-flow philosophy, except the two flows would now deliberately differ *by paradigm*, which is the honest way to find out whether the tradeoff earns its cost in this project's own stack rather than reasoning about it in the abstract.

**Phase 3 — decide, and log it.** Only migrate `check_order_status` and retire `IntentClassificationFlow`'s hardcoded routing role if Phase 2 concretely earns it: the digression gap measurably closes, and the prompt-size/latency/cost growth from §5 was actually measured against Phase 1's baseline, not assumed. Whatever gets decided — adopt fully, reject, or keep both paradigms permanently side-by-side for different flow shapes — belongs in `decisions-log.md` as a new, explicit D-entry with the measured evidence, not left implicit in this proposal doc.
